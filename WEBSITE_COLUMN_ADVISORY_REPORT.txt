HOW THIS COULD HAVE HAPPENED (AI / SCRIPT-DRIVEN MIGRATION)
================================================================================

None of this was done by hand; the data was brought over by AI/scripts. Plausible
ways an automated pipeline could have produced wrong websites:

1. Merge by row position instead of by key
   Aligning donor and target by row index (row 8 -> row 8) instead of by name/slug
   would misalign if row order differed. Donor row 8 = Ashley's Market; if output
   row 9 = Chicken Coop but was given donor row 8's website, Chicken Coop gets
   Ashley's URL. Same for Colleen, Corner Market, Graves, Hickman's if adjacent.

2. Forward-fill (ffill) or "fill missing from previous"
   After a merge, fillna(method='ffill') on website would copy the first non-empty
   URL (e.g. Ashley's) to every following row until the next non-empty. One URL
   would propagate to many rows in order.

3. Column index or CSV parsing error
   Wrong delimiter/quote handling or column indices could make "website" read from
   the wrong source column (e.g. one that repeated or was constant), assigning
   the same URL to many rows.

4. Group-by-type or "first of category" logic
   "For type = Markets & Delis, set website to the first website in that type"
   would assign one URL (e.g. Ashley's) to every listing in that category.

5. AI/LLM merge or "fill missing" without key matching
   Merging or filling without strict name/slug matching could match by position
   or "similar" text and repeat one URL, or infer a wrong rule (e.g. "all markets
   share one Facebook page").

6. Wrong column mapping in migration
   Website field wired to a constant or wrong donor column for a subset of rows
   (by index or condition) would repeat one URL.

7. Extraction from wrong row context
   Scripts that fill empty website by taking "first URL" from that row's
   description would copy a wrong URL if an earlier step had already put the
   wrong description (or wrong URL in the description) into that row.

8. Multiple CSVs merged without stable key
   Merging donor + other sources with missing/inconsistent key (name vs slug,
   spellings) could assign website from the wrong matched row or a single
   default/fallback.

Takeaway: The donor has correct per-listing websites. The error was introduced
in a step that wrote/updated the final CSV without strictly matching each row
to the donor by name or slug when copying the website field.

(Original manual-speculation items retained below for reference.)

1. Fill-down in a spreadsheet
   When the CSV was edited in Excel/Sheets, the website cell for Ashley's Market
   may have been filled down through the next several rows. Markets & Delis are
   often grouped together, so one URL could have been applied to multiple rows.

2. Copy-paste
   The Ashley's Market Facebook URL could have been copied and pasted into the
   website column for other market/deli listings under the assumption they
   shared a page or that it was a placeholder.

3. Merge/import script
   If a later script or import merged “external” website data by position or
   by type (e.g. “first Markets & Delis URL”) instead of by listing name/slug,
   one URL could have overwritten several rows.

4. Manual data entry
   Someone may have entered the same URL for multiple market listings by mistake.

The donor is the only source that has per-listing, correct websites; the final
CSV diverges for Chicken Coop and the other four (Colleen, Corner, Graves,
Hickman’s), so the error was introduced after the donor, during a step that
wrote or edited the final CSV.
